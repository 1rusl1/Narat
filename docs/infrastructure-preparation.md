# Narat — подготовка инфраструктуры и данных

Исходный план: 2026-11-02; scope актуализирован 2026-11-09. Объём: простой iOS MVP для Польши, PL/EN. Это план подготовки, не подтверждение, что внешние аккаунты уже настроены. Доступы к кабинетам в этой проверке не использовались; платные сервисы не создавались и API с оплатой не вызывался.

Инфраструктура, подготовленные данные, реализованный код и пройденная приёмка — отдельные условия готовности. Даже полностью настроенные кабинеты не устраняют незавершённые интеграции из [handoff](handoff_status.md).

## Первый стенд для iOS — решение от 6 ноября

Первый результат — сборка iOS на устройстве открывает карточку со стенда, сохраняет растение и получает его обратно из базы после очистки локального кеша при сохранённой сессии. Этот сценарий можно готовить параллельно с T148. Для проверки соединения достаточно небольшого согласованного набора карточек. Приёмка полного каталога по T149 зависит от T148.

1. Владелец предоставляет доступ к существующему тестовому Supabase или создаёт проект для Narat в регионе ЕС. Разработке нужны доступ к проекту, его URL и публичный ключ. Серверные секреты задаются в настройках окружения.
2. Разработка применяет 18 миграций на чистом стенде, фиксирует версию PostgreSQL (локальный конфиг указывает 15, последний отчёт приёмки — 17.11), включает гостевые сессии, загружает тестовые карточки и проверяет выдачу изображений с устройства. Для пользовательских фото отдельно нужны закрытое хранилище, правила доступа и проверка двумя владельцами.
3. Подключить маршруты каталога к точке входа plants-api, команды сохранения и синхронизацию — к БД. Сейчас штатный обработчик команд возвращает committed без записи, а синхронизация возвращает пустой список. В iOS формировать адрес API из URL окружения и проверить сессию гостя через шлюз функций. Фиксировать версию миграций и функций для каждой тестовой сборки.
4. На iPhone найти вид, открыть фото, сохранить растение, проверить строку в БД и повторное чтение через API. Второй пользователь должен видеть общую карточку, но получать отказ в доступе к чужим приватным данным. Зафиксировать сборку, окружение и результат.
5. Следующий независимый прогон — анализ снимка. Подключить рабочие адаптеры регистрации установки, приватной загрузки и очереди; защитить вызов обработчика, настроить запуск по расписанию, тестовый выпуск протоколов и ключ Anthropic с лимитом. Точка входа worker сейчас отвечает только статусом. Проверить на одном разрешённом фото результат на телефоне, а при ошибке — завершение задания и возврат квоты.

Apple/Google и подписки готовить параллельно по таблице ниже. Production разворачивать отдельно перед выпуском и повторять проверки с его конфигурацией.

## Что подготовить

| Компонент | Нужный результат | Кто делает |
|---|---|---|
| Supabase | Тестовый проект и отдельный production перед выпуском; регион выбираем с учётом рынка Польши, URL/project ref и публичный ключ | Владелец создаёт организацию/проекты и настраивает billing; разработка выполняет конфигурацию и deployment |
| PostgreSQL / Storage | Применённые миграции; закрытые фото/черновики, RLS и signed URL; импорт каталога/KB; проверка доступа двух владельцев | Разработка |

| Google OAuth | Cloud-проект, consent screen, iOS OAuth client для bundle ID, при необходимости server/web client под схему Supabase; разрешённые audiences и тестовые аккаунты | Владелец — проект/доступ; разработка — конфигурация |
| Anthropic | API-проект/ключ, доступ к `claude-haiku-5-5`, доступный бюджет/лимиты, порог расходов и уведомления | Владелец — billing/доступ; разработка — адаптер и ограничения |
| Подписки | Одна группа, продукты month/year, цены PL 49,99 zł/месяц и 199,99 zł/год, 7-дневный trial только для годового eligible; Sandbox accounts, Server API key и Notifications V2 URLs | Владелец — договоры/банковские/налоговые сведения; разработка — продукты и проверка событий |
| Разработка / CI | Git-репозиторий и CI, macOS runner для сборки/запуска iOS-тестов, Linux/Deno проверки, Docker-совместимый runtime для локальной БД и pgTAP | Разработка; владелец подтверждает доступ и лимиты сервисов при необходимости |
| Эксплуатация | Логи и алерты без фото/токенов, контроль очереди/ошибок/расходов, резервирование БД и объектов Storage, проверенное восстановление | Разработка, с выбранными владельцем лимитами расходов и сроками хранения |
| Публикация | Стабильные HTTPS-страницы privacy/условий/support, контакт поддержки; EN/PL metadata и screenshots, app icon, privacy declarations, сведения для Review | Владелец утверждает содержимое; разработка готовит материалы/сборку |

Отдельный VPS, Redis, Kubernetes или собственный API-домен текущей архитектуре не требуются. Для API можно использовать HTTPS URL проекта Supabase; жёстко заданный в коде адрес нужно заменить конфигурацией окружения. Домен для публичных страниц поддержки/документов выбирается отдельно.

Локальные напоминания уже выбраны архитектурой, поэтому APNs backend не является зависимостью MVP. SMTP понадобится при добавлении email-based входа/писем; сейчас основной вход — Apple/Google.

## Конфигурация и секреты

Существующие шаблоны: [supabase/.env.example](../supabase/.env.example), [Auth.xcconfig](../ios/Configuration/Auth.xcconfig), [настройка native auth](validation/native-auth.md).

- В приложении: Supabase URL и publishable/anon key, Google client IDs и callback scheme. Эти поля не предоставляют привилегированный серверный доступ.
- На сервере: Anthropic key; Supabase secret/service-role; internal worker secret; ключи подписи analysis/decision receipts и installation pepper; Apple API credentials; материалы для revoke Apple и ключ шифрования. Где ключи выдаёт сервис, использовать его кабинет; случайные внутренние ключи генерировать при настройке.
- Секреты размещать в Supabase Secrets/Vault и CI secrets, локально — в исключённых из Git файлах. Не требуются их публикация в чате, Git или сборке приложения.
- Sandbox/тестовые и production значения изолировать. Указать реальные webhook URLs и проверить тестовым событием, а не только сохранить строку в кабинете.
- Поля `.env.example` — шаблон: запись значения туда сама по себе не включает provider в Supabase и не создаёт Apple/Google client.

## Какие данные нужны

1. **Существующий каталог.** Стабильные ID, научные/EN/PL имена, фото и атрибуция. Сохранить фактический выпуск; минимального размера базы нет.
2. **Первая партия проверенных карточек.** Применимые действия сейчас, основания и условия следующей проверки, источник/права/EN-PL/версия. Полный профиль каждого вида и универсальный pipeline не обязательны.
3. **Фактически поддержанные проблемы.** Опубликованные IDs/признаки, unknown/healthy/out-of-scope, первая помощь и ограничения без фиксированного числа проблем.
4. **Источники и права.** Происхождение/допустимое использование и атрибуция; запись approved сама по себе не заменяет проверки.
5. **Качественные проверки.** Ранний малый набор отдельно; до публичного eval определить выборку и достаточность по T118, независимо разметить ожидаемые вид/проблему/действие и неизвестные случаи. Нет обязательного минимума 200.
6. **Продуктовые фикстуры.** A/B, guest/permanent, 0/3/4 растения, неизвестный вид, семь дней, offline/retry, trial/paid/expiry/refund; это не реальные пользователи.

## Устройства и проверка

- Физический iPhone для съёмки фото и native sign-in; для заявленной поддержки отдельно проверяются минимальная и актуальная iOS по матрице устройств.
- Sandbox-покупки: eligible/ineligible trial, restore, отмена/expiry/refund, monthly quota без повторной выдачи; правильная обработка подписанных server events.
- БД/Storage: RLS двух владельцев, идемпотентность, потери соединения, перенос фото до семидневного срока и отказ от восстановления удалённого draft, удаление аккаунта.
- Ранние качественные UX-прогоны EN/PL фиксируют участников, критерии и ограничения; универсальной квоты 20 на язык нет. Публичная приёмка требует исправления блокирующих ошибок и достаточного quality eval по T118.
- Резервная копия БД не включает сами объекты Supabase Storage: их копирование и восстановление проверяются отдельно.

## Порядок подготовки

**Для первого живого анализа с последующим входом:** тестовый Supabase, локальный Docker runtime, API-доступ Anthropic, Apple/Google clients, физический iPhone, небольшой проверенный и явно ограниченный тестовый KB-набор. Такой набор проверяет интеграцию, но не доказывает точность всего покрытия; публичный eval определяется T118.

**Параллельно:** подготовить небольшую проверенную партию карточек, EN/PL контент и независимую eval-выборку; настроить CI и проверки SQL/Storage.

**К этапу оплаты:** App Store Connect products, договоры/billing, Server API и Sandbox/Notifications V2. Не блокируют разработку бесплатного пути.

**Перед выпуском:** отдельное production-окружение, проверенный базовый каталог, фактическое покрытие проверенными карточками/действиями по SC-016 без минимального числа видов, реальные OAuth/покупки/удаление, наблюдаемость и восстановление, TestFlight, quality/performance/usability и release gates.

Даже после подготовки остаётся реализовать незавершённый код из handoff: реальные адаптеры, рабочий worker, серверный анализ, перенос/коллекцию и остальные продуктовые функции. Критерий полного рабочего MVP — пройденные сценарии приёмки в целевых окружениях.
