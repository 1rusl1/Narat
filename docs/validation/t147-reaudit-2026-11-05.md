## Оставшиеся замечания

### 1. P1: конкурентный upsert нарушает изоляцию активного релиза

`supabase/migrations/202611050001_catalogue_skeleton.sql:295–298,474–476`.

`upsert` читает `v_release.state` без блокировки и позже принимает решение о материализации по устаревшему значению. `publish_catalogue_release` блокирует строку релиза, но `upsert` не участвует в этом протоколе.

Воспроизведено двумя соединениями PostgreSQL:

1. Импортировать и опубликовать v1; подготовить v2 с тем же `plant_id`.
2. Соединение A: `BEGIN; SELECT publish_catalogue_release(v2); SELECT pg_sleep(5); COMMIT;`.
3. Пока A ожидает перед COMMIT, соединение B вызывает `upsert_catalogue_skeleton_species(v1, record_with_changed_name, true)`.
4. B читает ещё видимое `v1.state='published'`, ждёт блокировку строки taxon и после COMMIT A перезаписывает её данными v1.

Фактический результат: активный релиз `audit_v2`, у строки вида `release_id=11111111-1111-4111-8111-111111111111` (v1), имя `Audit stale v1`, `get_catalogue_species_card(...) IS NULL = true`. Оба вызова завершились успешно. Вид из нового релиза исчезает из выдачи.

Нужен общий протокол блокировок импорта/публикации с согласованным порядком и конкурентный regression-тест. Последовательного rollback-теста недостаточно.

### 2. P2: SQL и общий валидатор не обеспечивают заявленный строгий контракт

`supabase/migrations/202611050001_catalogue_skeleton.sql:308–348`;
`catalogue/import.ts:622–663`.

На копии реальной записи установлены `hero_image.width=-1`, `wikidata_id='not-wikidata'`, `descriptions.en.language='fr'`. SQL upsert в активный релиз успешно записал всё это; публичная карточка вернула те же значения. TS `validateAndProjectSkeletonRelease` отклоняет такую запись по всем трём полям. Общий `validateCatalogueSkeletonCardContract` обнаруживает только неверный язык.

Дополнительная проба общего валидатора: после восстановления `description.language='en'` поля `taxon_id=42`, `common_names='oops'`, `care_profile_available='yes'` приняты с `errors=[]`. Проверка 21 ключа не подтверждает типы DTO. В handoff при этом заявлены проверки размеров, Wikidata ID, языка и URL как в TS, так и в SQL.

Нужно определить обязательные поля и типы общей схемой, валидировать реальные SQL-ответы этой схемой и не допускать публикацию записей, её нарушающих. Добавить независимые отрицательные проверки каждого поля.

### 3. P2: контракт не описывает реальные null в сезонных интервалах

`specs/001-plants-ios-mvp/contracts/api.md:223` обещает целые `1..365`. TS-модель допускает `number | null`, SQL также пропускает null. У **50 из 606** реальных видов есть null хотя бы в одном сезоне. Например, у `colocasia_esculenta` `winter=null`.

До T149 нужно явно описать nullable-сезоны, смысл отсутствующего интервала и исключение для `immersion`, чтобы клиент не декодировал все четыре значения как обязательные числа.

### 4. P2: число проверок не совпадает с TAP-планом

`supabase/tests/catalogue_skeleton.test.sql:12` задаёт `plan(26)`, но файл выполняет **28** assertions: последние две находятся на строках 546 и 556. Это несоответствие TAP-плану; заявление «26/26 TAP PASS» не подтверждается текущим файлом. Нужно исправить план и запускать настоящий pgTAP с проверкой итогового результата и количества assertions.
