# Отдельная учётка для технической приёмки — 25 ноября 2026

Создана ровно одна отдельная подтверждённая учётка только в `narat-staging`. Использован административный `createUser` с подтверждением адреса, без приглашения и отправки письма. В продукт не добавлялась регистрация по email; используется уже существующий экран входа. [Официальный метод Supabase](https://supabase.com/docs/reference/javascript/auth-admin-createuser).

Реальные проверки: создание — HTTP 200; обычный password token exchange — 200; чтение `/functions/v1/plants-api/me` от имени новой учётки — 200. Проверена постоянная, не анонимная идентичность. Это живая Auth/API-проверка, **не прохождение экрана входа на Simulator**. [Безопасные результаты](tester-separate-account-2026-11-25.json).

Email и пароль находятся только в `build/private/tester-account-20261125/login.json` (Git-ignored, режим 0600; каталог 0700). Service-role ключ использовался только в памяти, не записывался и не выводился. Токены входа также не сохранялись. В Git и чат credentials не помещались. Production и чужие учётки не менялись.

Для технического тестировщика: получить этот файл у владельца по согласованному защищённому каналу; в приложении открыть My plants → Sign in и ввести поля email/password. Синтетический адрес не принимает письма: это отдельный тестовый доступ, не личный аккаунт и не маршрут восстановления пароля. Не прикладывать login.json к баг-репортам, Git или общему архиву сборки.

Следующий шаг: после принятия AUTH-B проверить обычный экран входа новой сборки; результаты fixture-тестов и живого Auth/API не подменяют эту проверку. Для Google используется самостоятельный вход владельца, этот файл для него не требуется.
