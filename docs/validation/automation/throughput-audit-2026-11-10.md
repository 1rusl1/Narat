# Скорость разработки A/B — снимок 10 ноября 2026

**Последующее решение:** владелец разрешил реализацию предложений без запуска очередей.
Engine/config обновлены и проверены 147 локальными тестами; детали и ограничения —
в актуальном разделе [handoff](../../handoff_status.md). Измерения и предложения ниже
сохраняют снимок до реализации; нового live benchmark не было.

## Решение владельца

Оба оркестратора остановить перед изменением конфигурации. Автоматического
возобновления нет. GitHub Actions и дальнейшая работа над CI отложены;
T006 остаётся открытой и не блокирует разработку. Локальные продуктовые проверки
сохраняются. Конфигурация и код оркестратора этим аудитом не изменены.

## Измерения

[Сохранённый агрегат и список run directories](throughput-audit-2026-11-10.json).

Источник: сохранённые `state.json` в `docs/validation/automation/runs/orchestrator-parallel-*`
двух worktree, включая старые неудачные попытки. Чтение выполнено во время работы,
поэтому это снимок до остановки, а не окончательные итоги ночи.

| Показатель | A — iOS | B — backend |
| --- | ---: | ---: |
| Run directories с state | 42 | 7 |
| Завершённые попытки задач | 23 | 8 |
| Модельные вызовы | 100 | 33 |
| Сумма времени модельных вызовов, мин | 361,1 | 135,2 |
| Из них Developer, мин | 289,2 | 119,3 |
| Из них Review + QA, мин | 71,9 | 15,8 |
| Сумма времени записанных checks, мин | 102,1 | 10,5 |
| Тайм-ауты по 900 секунд | 5 | 3 |
| Совмещённая acceptance / delta resume, вызовы | 0 / 0 | 0 / 0 |

Суммы не являются временем по часам: A и B работали параллельно. Внешняя работа
управляющих чатов, подготовка вручную, ожидания пользователя и не записанные в
state команды в суммы не входят. Завершённые попытки — внутренние срезы, не число
закрытых продуктовых ID. B имела ещё RUNNING/PENDING записи в момент чтения.

CLI counters имеют неоднозначный per-turn/session scope, quota=null. Их нельзя
складывать в точный расход подписки или объяснять ими оставшиеся у владельца 56%.
Новых модельных прогонов или live-интеграций для аудита не запускалось.

## Что замедляет

1. **Developer занимает около 82% модельного времени.** Восемь тайм-аутов сами
   заняли около 120 минут. Ещё одна B попытка завершилась `cli_error` после
   783 секунд из-за неверного fingerprint ответа. Простое увеличение числа
   параллельных управляющих чатов не исправит эти потери.
2. **Повторная подготовка и приёмка исправлений инфраструктуры.** A создала 42
   run directories; часть остановок связана с target membership, интерфейсом
   gates, исчерпанием попыток и отсутствующим сравнительным diff. Например,
   `parallel-ios-ci-b1-sql` прошёл проверки, но QA не получила точную дельту.
   Не каждое BLOCKED означает дефект продукта.
3. **Проверки требуют времени, но не являются главным расходом B.** В A большая
   часть записанного времени checks — UI (~47,6 мин), unit/build (~35,5 мин),
   Simulator (~9,2 мин). У B все записанные checks суммарно ~10,5 мин против
   ~135 мин моделей. SQL/Deno нельзя считать основным узким местом B.
4. **Уже готовые controller candidates всё ещё получают Developer.** Текущий
   access HTTP manifest B прямо описывает готовый кандидат с локальными PASS;
   Developer затем вернул его без правок. Read-only acceptance уже поддерживается
   текущим engine и позволяет убрать такой лишний вызов.
5. **CI отвлекает от продукта.** В A восемь CI-вызовов занимают ~8,7 мин модели;
   отдельно не измерено время управляющего чата на подготовку/публикации. CI
   следует отложить, но это само по себе не устранит Developer timeouts.

Независимая приёмка выявила реальные дефекты rollback watermark и потери resume
pointer после SQLite ACK failure. Поэтому для хранения/квот/Auth/owner boundaries
нельзя просто отменить Review/QA ради скорости.

## Предложение для обсуждения конфигурации — ещё не применено

- Developer получает ограниченную реализационную задачу с точными входами,
  API/DTO и файлами. Reasoning выбирать по сложности реализации; высокий риск
  должен сохранять строгую независимую приёмку. Сейчас `route_level` для Developer
  использует максимум risk/complexity: смена этого правила потребует отдельного
  изменения engine и проверки, а не скрытого занижения task.risk.
- Готовые кандидаты принимать через `write_files=[]` без Developer. После
  замечания — отдельный ограниченный repair. Для high risk оставить обе роли
  Reviewer и QA; совмещённая acceptance допустима только для действительно простых
  low-risk/low-complexity задач в рамках уже существующего правила.
- Перед вызовом модели детерминированно проверить base/candidate diff, критерии,
  доступность логов/fixtures и Xcode target membership. При read-only acceptance
  передавать точный comparative diff, а не пустой task.patch.
- Выполнять проверки затронутых областей. Не добавлять полный SQL/Deno/UI suite
  к каждому изменению документации или простому клиентскому DTO без причины.
  Обязательные scope/criteria checks не обходить; совпадение только исходного
  кода при изменившемся контракте не даёт права переиспользовать evidence.
- Работать пакетами одного проверяемого поведения; уменьшать пакет после
  timeout, но не дробить каждый файл в отдельный полный цикл. Не повторять
  неизменённый неудачный запрос, не править старые state/fingerprint.
- Handoff читать по актуальному краткому разделу и Project State; полную историю
  (~317/323 KB в A/B) открывать только при конкретной необходимости. Engine уже
  передаёт Project State, размер handoff не доказывает его полную отправку модели.
- После возобновления сначала закончить B access/installations API и A T036,
  затем двигаться по продуктовому пути. Измерять модельные минуты, тайм-ауты и
  время до принятого сценария; экономию лимита пока не обещать.

Новые модели, провайдеры, число контроллеров и reasoning settings не изменялись.
Справка о выборе модели/reasoning: [официальная документация OpenAI](https://learn.chatgpt.com/docs/models?surface=web).

## Следующий шаг

Подтвердить остановку обеих очередей и отсутствие дочерних процессов. Согласовать
