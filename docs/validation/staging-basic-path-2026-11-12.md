# Общий прогон распознавания, коллекции и ухода

## Стенд перед прогоном

Связанный PostgreSQL-запрос подтвердил 44 миграции до `202611120023`. CLI подтвердил активные `plants-api` v14 и `analysis-worker` v7. Опубликованы каталог `skeleton-300-v1-en-85fcaba4` (`81bb49c1-0e39-5a9c-8327-7be12075f4ad`) и care KB `staging-monstera-care-v2` (`3ed50000-0000-4000-8000-000000000012`). `analysis-inputs` приватный, `catalogue-media` публичный. UUID вида Monstera deliciosa — `83f27806-3577-4bdc-9b18-222bedcf06d7`.

Отдельная прежняя тестовая учётная запись прочитала семь изменений и обе настройки уведомлений в `/sync`. Живой GET для её Monstera вернул `check_soil`, условный полив после лёгкого подсыхания и `next_check_interval_days: null`. Подтверждены 401 без сессии, 404 для неизвестной карточки и чтение исторического диагноза. [Источник рекомендации в опубликованном профиле](https://hort.extension.wisc.edu/articles/monstera-deliciosa/).

До получения UUID нового прогона сервер повторно прочитал прежние тестовые данные на том же стенде. Живые provider jobs вернули `identified/consumed` с каноническим UUID Monstera и `unknown/released` с null. PostgreSQL подтвердил вызов провайдера, оба quota outcome и закреплённый релиз. GET карточки `197bd854-6324-44cb-81e2-29d3cab37d13` вернул 442 566 байт исходного фото с совпавшим SHA-256, 401 без сессии и 404 для второго владельца. PostgreSQL подтвердил связь фото с карточкой, её владельца и наличие объекта в приватном bucket. Три сохранённые карточки отдельного Free-владельца без профиля вернули `200 unavailable/null`.

Для прежней карточки `276ffeec-1522-4b42-b290-e6c07860f8d8` две новые постоянные сессии сверили точный HTTP replay обоих существующих receipts. `care.record` вернул исходный receipt со state `active`, `care.undo` — исходный receipt со state `voided`. Полный `/sync` до и после одинаковый. В текущем журнале одна отменённая запись `4e9c6512-f048-4c3a-b2b9-ecc51a89ca15` и один reversal `fa0e5a73-ecad-4eda-98a9-9e07ef46a549`. PostgreSQL подтвердил те же строки и оба receipts.

Новые пользовательские записи выполнил A из подписанной EN-сборки `f74f12f` под одним изолированным владельцем. B сверил те же UUID без создания записей. Действующие квоты сохранены. [Опубликованный отчёт iOS](https://github.com/1rusl1/Narat/blob/412dfdf/docs/validation/mvp-acceptance.md).

## Общий живой прогон на одном владельце

Staging SQL и подписанная iOS-сборка сверены по одному новому постоянному владельцу `b35efa69-337c-43bd-be8d-00a7addf1bc9`. До прогона A подтвердил пустые коллекцию, журнал и очередь identification.

- В обоих заданиях зафиксирован старт провайдера. Синтетическое непригодное фото — job `5c244f72-f420-40ba-a3bf-cd37972a160b`, `succeeded / unknown / released`, taxon null. Monstera — job `f20ed02e-199f-4f89-b299-d6faef4ae070`, `succeeded / identified / consumed`, канонический taxon `83f27806-3577-4bdc-9b18-222bedcf06d7`. Оба задания закрепили текущий каталог.
- Владелец сохранил ровно две карточки. Monstera `bdb0a216-cbc3-48fd-aac8-b5f0f0aa7b39` ссылается на фото задания `3af3930f-f4e5-4141-8cf5-1e1a5b8798ab`. Совпали владелец, привязка, состояние `ready` и объект в приватном bucket, 574 412 байт. HTTP фото вернул 401 без сессии и 404 второму владельцу. iOS восстановила ту же карточку и фото после потери ответа на сохранение и холодных запусков.
- Публичные карточки по каноническим UUID вернули `care_profile_available=true` для Monstera и `false` для Adenium arabicum. Owner RPC для Monstera вернул профиль активного KB с `check_monstera_mix_before_watering` и UW Extension. Для Adenium `552de757-b36e-46a2-81ca-2fef720f5d97` тот же RPC вернул null profile. iOS отобразила оба исхода, включая отсутствие проверенной рекомендации после холодного запуска Adenium. [Источник Monstera](https://hort.extension.wisc.edu/articles/monstera-deliciosa/).
- SQL подтвердил исходный `active` receipt операции `68eee192-732a-4a18-865a-0e9fef59e432` и `voided` receipt undo `b1f5b958-8f82-4209-8207-55dbc56895cb`. Каноническая `owner_sync_entries` выдаёт ровно одну отменённую запись `d2b2eb32-5bc3-4e1d-b3c0-c7d1f19f01b1` и reversal `07399679-b153-4e73-87f1-3650c1941104`. A отбросил первый успешный ответ `care.record` на клиенте, повторил ту же операцию после запуска и прочитал сначала `Active`, затем `Undone` после undo и ещё одного запуска. Независимый HTTP replay обоих receipts с двумя новыми Auth-сессиями проверен выше на прежнем владельце.
