## Замечания

1. **P1: публичный доступ к SECURITY DEFINER записи.**
   `supabase/migrations/202611050001_catalogue_skeleton.sql:16`: функция
   upsert_catalogue_skeleton_species меняет каталог с полномочиями владельца,
   принимает произвольную запись и по умолчанию публикует её. В миграциях нет REVOKE
   EXECUTE FROM PUBLIC или проверки вызывающего. В стандартном PostgreSQL новые
   функции доступны PUBLIC; RLS не заменяет ограничение SECURITY DEFINER.
   Отозвать права PUBLIC/anon/authenticated и разрешить только доверенному импорту.
   Это вывод по коду; удалённые роли/фактический RPC-доступ не проверялись.

2. **P1: чтение не изолировано активным релизом.**
   `search_catalogue_species` допускает любой published taxon, когда активного
   catalogue_releases нет (условие v_release.id IS NULL), и записи release_id IS NULL.
   `get_catalogue_species_card` (строки 462–470) вообще не проверяет релиз.
   Поэтому запись, добавленная с p_publish=true в draft/retired релиз, доступна
   по прямому идентификатору, а при отсутствии активного релиза — и в поиске.
   Дополнительно upsert по уникальному plant_id перезаписывает текущий taxon при
   подготовке следующего релиза; атомарная смена релиза не сохраняет прежний снимок.
   Нужны единые правила видимости, изоляция staging и тесты draft/retired/переключения.

3. **P2: API-контракт не совпадает с SQL/TS.**
   `contracts/api.md:220–224` описывает description.lang, парные сезонные диапазоны
   watering.interval_days.spring_summer/autumn_winter и плоские safety.cat/dog.
   Проекция возвращает description.language, watering.intervals_days с четырьмя
   сезонами и safety.cat/dog как объекты status. Несколько обещанных полей отсутствуют.
   Выбрать одну структуру и проверить SQL/TS по общей схеме до реализации T149.
   Поиск также обещает игнорирование диакритики и поиск по семейству, но нормализация
   лишь lower/trim, а family не участвует в WHERE.

4. **P2: валидатор проверяет наличие, а не корректность полей.**
   `catalogue/import.ts:566–570`: sha256 и intervals_days проверяются на truthiness.
   В отдельном Deno eval на копии реального bundle поставлены sha256='not-a-hash'
   и интервалы {spring:-7,summer:'bad',fall:0,winter:null}; получено valid=true,
   errors=[]. Исходный JSON не менялся. Нужны проверки формата/значений и negative tests.
