# T152 — безопасный отказ вместо демонстрационного результата

Дата: 2026-11-08. Приняты два ограниченных среза через оркестратор; полная T152 остаётся открытой.

## Реализовано

- API без подключённых persistence handlers возвращает HTTP503 `INTERNAL_ERROR`, `retryable=true`, EN/PL. Нет фиктивного `committed` и пустой успешной sync-страницы; auth/account guards и переданные handlers сохранены.
- iOS по умолчанию не выдумывает квоту, фото, диагноз, совет или receipt. Care/scan и problem/scan показывают недоступность с повтором, возвратом и каталогом. Повтор сохраняет operationId и ввод; генератор изображений перенесён в test target.
- При сетевом отказе sync, включая отказ после промежуточной страницы и при full refresh, подтверждённый кеш/watermark сохраняются: страницы сначала собираются, затем применяются. HTTP503 не очищает outbox.

API: `supabase/functions/plants-api/index.ts`, `supabase/functions/_shared/tests/persistence_unavailable_test.ts`.

iOS: `ios/Plants/Data/Sync/SyncEngine.swift`, `ios/Plants/Features/Analysis/AnalysisFlowModel.swift`, `ios/Plants/Features/Analysis/CareQuestionsView.swift`, `ios/Plants/Features/Analysis/PreliminaryResultView.swift`, `ios/Plants/Features/Catalogue/GuestCatalogueView.swift`, `ios/Plants/Features/Onboarding/AddPlantRouter.swift`, `ios/PlantsTests/FirstHelpUnitTests.swift`, `ios/PlantsTests/SyncPersistenceTests.swift`, `ios/PlantsUITests/FirstHelpTests.swift`.

## Ограничения и точный следующий шаг

Живые модели и локальный Simulator проверены реально. Deployed backend/Auth/Storage, физическая камера и реальное identification не проверялись и не развёртывались. HTTP503/outbox проверены test transport; пересоздание LocalStore использует тот же inMemory container, а не холодный перезапуск процесса. Атомарность применения полного snapshot при сбое диска/процесса не принималась. Каталог в isolated build честно сообщает об отсутствии подключения; его данные и сохранение здесь не принимались.

T152 не закрыта; остальные checkbox не менялись. Следующий шаг: проверить доступность и версию текущего staging, подготовить отдельный manifest проверки T152 на живом API (`commands`/`sync`, guards, повтор без ложного committed) и проверки pending на дисковом store после перезапуска. При необходимости сначала подготовить развёртывание проверенной версии с явной идентификацией стенда. После приёмки T152 — T148: редакционная приёмка 606 карточек, затем T149. T150/T151 и T154 не заменяются этими тестами.
