## Реализация

1. **Конкурентная публикация.** Upsert и публикация берут одну транзакционную advisory-блокировку `public.catalogue_releases_mutex`, затем блокировку строки релиза, затем вида. Состояние целевого релиза читается после получения mutex с `FOR UPDATE`. Прямое изменение `catalogue_releases` использует ту же блокировку в `BEFORE STATEMENT`, до блокировки строк. Воспроизводимый тест держит первую транзакцию открытой, проверяет в `pg_locks`, что второе соединение ждёт именно advisory-блокировку, и только затем выполняет COMMIT. Проверены оба порядка импорта/публикации и прямой UPDATE релиза. После каждого сценария карточка доступна и содержит имя и release_id v2; старый импорт меняет только снимок v1.
2. **Общая схема и строгие типы.** `contracts/catalogue-skeleton.schema.json` содержит `definitions.card` (все 21 ключ обязательны, лишние верхнеуровневые ключи запрещены) и `definitions.record` (вход импорта с явно заданными обязательными полями). Её использует Ajv в `catalogue/import.ts`; SQL содержит синхронизированный JSON и проверяет тот же набор ключевых слов. `sync_catalogue_schema.py --check` проверяет совпадение и запрещает добавлять неподдерживаемые SQL ключевые слова. Проверяются UUID/QID, boolean, массивы имён/алиасов, вложенные объекты, положительные размеры/байты, SHA-256, URL, языки/атрибуция описаний и интервалы. Снимки проверяются при INSERT/UPDATE и повторно при активации; испорченный старый снимок не публикуется, предыдущий релиз остаётся активным. В TS устранено приведение `care_profile_available` к boolean; nullable-типы объектов согласованы со схемой. Необязательный `hero_image.mime` явно отражён в модели: в реальных исходных записях его нет. SQL и TS также одинаково обрабатывают явный genus и пробелы в локализованном имени.
3. **Nullable-сезоны.** API, data-model и pipeline требуют четыре ключа с `int 1..365 | null`. Null означает отсутствие регулярного интервала у источника: клиент не подставляет 0/другой сезон и не выводит из этого запрет полива. Требуются минимум два числовых сезона; `watering_method='immersion'` разрешает все четыре null. Объект watering и оба описания у опубликованной базовой карточки обязательны.
4. **Настоящий TAP.** План SQL-файла — `plan(229)`, фактически выполнены 229 assertions. В runner дополнительно проверяется равенство плана и числа assertions, результат разбирается стандартным Perl `prove`; ненулевой результат останавливает прогон. Использован настоящий upstream pgTAP из тега v1.3.4 (`make`, затем загрузка `sql/pgtap.sql`), без assertion-обёрток.

## Воспроизведение

Нужны PostgreSQL >=15, роли anon/authenticated/service_role, Deno, psql, Perl prove и настоящий pgTAP. Runner сам создаёт отдельную БД, применяет исходные миграции, запускает проверки и удаляет только созданную им БД. Параметры подключения — PGHOST/PGPORT/PGUSER. На окружении с установленным расширением достаточно:

```sh
python3 supabase/tests/run_catalogue_regression.py
```

Для проведённого прогона использовалось:

```sh
PGHOST=/private/tmp PGPORT=55480 PGUSER=postgres \
python3 supabase/tests/run_catalogue_regression.py \
  --psql /opt/homebrew/opt/postgresql@17/bin/psql \
  --pgtap-sql /private/tmp/pgtap-1.3.4/sql/pgtap.sql \
  --output-dir /private/tmp/t147-regression-verified
```

Временный кластер PostgreSQL после проверки остановлен. Для повторения команды его нужно запустить заново либо задать подключение к другому локальному серверу. Установленный PostgreSQL 17 не подменяет связанную с PATH версию PostgreSQL 14.
