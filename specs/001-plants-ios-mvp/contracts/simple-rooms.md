# Простые комнаты — отдельная задача возврата

Статус: **запланировано, не реализовано**. Задачи T172–T174 в [пакетах оркестратора](../orchestrator-cleanup-tasks.md). Текущий room retirement остаётся действующим до принятия новой forward migration. Возврат не блокирует MVP.

В обсуждении согласована идея: комнаты как простая группировка коллекции — название, список растений, фильтр. Поручение 9 ноября: создать задачу возврата. Детали ниже — минимальные проектные решения для этой задачи, не утверждение о ранее реализованном UI.

## Поведение

- Комната принадлежит одному постоянному аккаунту и содержит только название и технические ID/owner/timestamps/tombstone. Никаких условий освещения/влажности/сезона, общего ухода или AI.
- У растения не более одной комнаты; отсутствие комнаты нормально. Фильтры: «Все», «Без комнаты», конкретная комната. Нет вложенности, sharing, автоматической классификации и отдельной квоты комнат.
- Создать, переименовать, удалить комнату; назначить или снять комнату у уже сохранённого растения. Название после trim — 1–80 символов; одинаковые названия допустимы, идентичность по UUID. Старые названия читаются без автоматического переименования.
- Назначение комнаты необязательно и выполняется после подтверждённого сохранения растения. Guest draft/claim и plant.create не получают room input или inline create_room_name обратно. Старые guards этих путей сохраняются; новая отдельная команда назначения работает с существующим экземпляром.
- Удаление комнаты не удаляет растения: они попадают в «Без комнаты». История/фото/анализы/условия и расписание растения неизменны. Room-only изменение не делает анализ stale и не перезапускает уход.
- Доступно владельцу на Free и paid, в том числе после expiry: это организация личных данных. Лимит добавления растений и запрет автоматики после expiry сохраняются отдельно.

## Данные и команды

Использовать сохранённые `rooms` и `plants.room_id`, существующий operation receipt и owner-scoped sync/outbox. Ввести только новую migration; не откатывать `202611090002_retire_rooms.sql`. Переиспользовать room.create/rename/delete через текущий command protocol, для существующего растения — отдельную `plant.set_room` с nullable room_id. Конкретные HTTP/RPC сигнатуры зафиксировать до реализации в API/sync addendum; запрет прямых клиентских записей и owner isolation сохранить.

Room CRUD/assignment идемпотентны по operation_id и hash payload. Точный старый receipt возвращается без повторного side effect. Удалённые/чужие room/plant отвергаются. При concurrent assign/delete единый lock order сериализует операции: assignment к уже удалённой комнате отклоняется, delete после assignment очищает связь. Новый timestamp/watermark отражает и изменения связей, чтобы клиенты получили «Без комнаты».

В delta возвращаются комнаты и nullable plant.room_id; private fields не расширяются. Tombstone комнаты не удаляет растение и не теряет pending клиента. Full refresh, pagination, logout/owner switch используют текущую инфраструктуру. Не заводить второй sync/кеш/outbox ради комнат.

Старые неудалённые комнаты владельца снова показываются с прежними UUID/названиями/связями. Ссылка на удалённую/недоступную комнату отображается как «Без комнаты»; история не переписывается и автоматическая массовая очистка пользовательских данных не требуется. До записи проверить фактические legacy rows и FK/RLS. Тесты с room retirement сохраняются как исторический checkpoint, новые приёмочные tests проверяют новый контракт поверх всей последовательности миграций.

## Приёмка

SQL clean/seeded upgrade, A/B owner isolation, service-only grants, real retry/assign-delete concurrency, sync/tombstones; Deno API behavior; Swift persisted offline/restart/full refresh и EN/PL UI. Отдельно live test с двумя owners и двумя клиентами одного owner. Нет скрытого возврата Free-мест, local_fallback, сезонных override, AI-follow_up, товарного таймера или обязательного room step. Точные AC — T172–T174.
