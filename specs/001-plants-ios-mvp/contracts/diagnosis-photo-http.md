# Фото и диагноз для тестового аккаунта

Первый срез использует активный постоянный аккаунт. На всех запросах передавайте `Authorization: Bearer <access_token>` и `X-Client-Locale: en` или `pl`.

1. `POST /media/upload-ticket` принимает `operation_id` (UUID), `mime_type`, `byte_size` и `content_sha256` (64 шестнадцатеричных символа нижнего регистра). Клиент отправляет нормализованное фото без EXIF. Допустимы JPEG, PNG и WebP до 10 МиБ. Ответ 200 содержит `photo_asset_id`, `storage_bucket`, `storage_path`, `signed_upload_url`, `expires_in_seconds`, `max_byte_size`. Один `operation_id` связан с одним фото и исходными метаданными. При конфликте сервер отвечает 409. Просроченное фото без загрузки требует нового `operation_id`.
2. `PUT` по `signed_upload_url` с тем же Bearer и `Content-Type` передаёт сырые байты. Ссылка ведёт на `plants-api` и действительна 60 секунд. Сервер проверяет сессию, владельца, длину, подпись формата и SHA-256, пишет в приватный Storage и отвечает `200 {"photo_asset_id":"…","state":"ready"}`. Не передавайте Bearer на другой origin. При потере ответа `POST /media/complete {"photo_asset_id":"…"}` проверяет готовность фото и возвращает тот же результат.
3. `POST /analysis/jobs` принимает отдельный `operation_id`, `mode: "diagnosis"` и `photo_asset_id`. Повтор ID команды загрузки возвращает 409 `IDEMPOTENCY_CONFLICT`. `flow_id` (UUID) опционален. Первое создание возвращает 202, точный повтор 200 с тем же `job_id`. `GET /analysis/jobs/{job_id}` возвращает текущее состояние. В обоих ответах есть `job_id`, `mode`, `status`, `quota_kind`, `quota_state`, `result`, `error_code`, `error_message`. Статусы `queued`, `running`, `succeeded`, `failed`, `expired`. Пока результата нет, `result` равен `null`.
4. При `succeeded` поле `result` содержит существующий `PreliminaryAnalysisProjection`. Для результата фото используйте `identification_status`, `plant_id`, `diagnosis_status`, `selected_condition_id`, `candidates`, `limitations`. `plant_display_name` и `condition_display_name` могут быть `null`. Они берутся из закреплённых опубликованных записей. Допустим результат `unknown` или `insufficient_data`. Техническая ошибка возвращается как `failed` с кодом ошибки. `GET` доступен только владельцу.

Этот контракт описывает первый тестовый путь. Подтверждение исполнения в стенде и реального ответа провайдера фиксируется в handoff после прогона.

## Повторная диагностика сохранённого растения (V02)

Постоянный владелец получает ticket и загружает новое приватное фото тем же способом. `POST /analysis/jobs` использует прежний envelope с дополнительным UUID сохранённого экземпляра.

```json
{
  "operation_id": "17000000-0000-4000-8000-000000000041",
  "mode": "diagnosis",
  "photo_asset_id": "17000000-0000-4000-8000-000000000042",
  "target_plant_id": "17000000-0000-4000-8000-000000000043"
}
```

`target_plant_id` разрешён только в `diagnosis`. Это UUID карточки владельца, отличный от идентификатора вида в `result.plant_id`. Клиент сохраняет исходный envelope, включая опциональный `flow_id` и локаль. Первый ответ 202 и точный повтор 200 содержат тот же `job_id`, `target_plant_id` и `photo_asset_id`. Текущий результат читается прежним `GET /analysis/jobs/{job_id}`. Для других заданий новых полей нет.

Сервер проверяет существование активной карточки и готового фото у текущего владельца перед резервом. Для удалённой, чужой или неизвестной карточки либо недоступного фото возвращается 404, для гостя — 403. Изменение принятого envelope под прежним ID даёт 409 `IDEMPOTENCY_CONFLICT`. Успешно использованное фото или фото, принадлежащее другой карточке или операции, даёт 409 `PHOTO_ALREADY_USED`. После технического сбоя клиент может отправить тот же upload с новым ID операции для той же карточки. Действуют штатные квоты и сроки.

На момент принятия сервер фиксирует актуальные свет, частоту полива, дренаж и до 12 последних фактических записей ухода этой карточки. Отсутствующие условия остаются неизвестными, пустой журнал допустим. AI получает только новое фото и эти данные без свободного текста, прежних фото, диагнозов и сравнения. Задание хранит ссылку на новое фото и карточку. Главное фото, предыдущие результаты и журнал сохраняются.

## Действие первой помощи, доступное для записи (V19)

Owner `GET /analysis/jobs/{job_id}` может добавить верхнеуровневое поле `first_aid_action`:

```json
{
  "job_id": "17000000-0000-4000-8000-000000000041",
  "plant_id": "17000000-0000-4000-8000-000000000043",
  "action_id": "check_monstera_moisture",
  "action_code": "check_soil",
  "source": {
    "url": "https://www.rhs.org.uk/plants/swiss-cheese-plants",
    "locator": "Preferences and Dislikes"
  }
}
```

Поле есть только для успешного привязанного диагноза с текущими условиями и допустимым опубликованным действием. Сервер требует прямую опору действия в одобренном HTTPS-источнике. После записи, включая отменённую запись, поле отсутствует. Оно также отсутствует для queued, healthy, unknown, непривязанных и устаревших заданий. Создание и replay POST сохраняют прежний формат.

Клиент показывает кнопку только при наличии поля и совпадении обоих UUID с текущими job и карточкой. Текст результата предназначен для отображения. Поле допускает запись факта даже без срока контроля. `care.first_aid.record` повторно проверяет право на действие, источник и дубликат. [Команда записи](manual-care-journal-http.md).
