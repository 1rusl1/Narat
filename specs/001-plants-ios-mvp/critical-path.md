# Критический путь Narat до MVP

Решение 11 ноября 2026: разработка и приёмка на английском. Переключатель EN/PL и польская приёмка сняты с объёма MVP. Существующие польские данные, язык истории и совместимость форматов сохраняются. Миграция двуязычных форматов не нужна для первого прогона.

| Порядок | Что делаем | Когда считаем пройденным |
| --- | --- | --- |
| 1. Фото → результат | Доводим существующий путь на staging: T031–T034, T037–T039, T157. | Минимум уже проверен: два реальных запроса из Simulator, результат и явная неопределённость. Остальные ветки принимаем до выпуска, применимый совет проверяем на шаге 3. |
| 2. Результат → карточка | **Следующий пакет:** срез T044/T046–T049/T150. Подключаем подтверждённый вид из результата к существующему `plant.create` в постоянной тестовой сессии. Оставляем один вход; фиксируем EN и убираем переключатель в затронутом iOS-пути (часть T170). | API подтверждает создание, клиент читает реальную карточку с тем же ID; после перезапуска карточка доступна. Повтор после потерянного ответа не создаёт дубль; при ошибке фото и ввод сохраняются. |
| 3. Карточка → уход | Срез T055–T056/T062–T068/T171: одно применимое действие из проверенных данных и запись факта через `care.record`. | Пользователь видит действие с основанием и следующей проверкой, если она обоснована. Запись сохраняется и видна после перезапуска; повтор не дублирует, отмена работает. При недостатке данных нет фиктивного совета. |
| 4. От живого среза к выпуску | По завершении 2–3 принимаем оставшиеся ветки: каталог и identification-only (T148–T151), guest/auth, квоты и StoreKit, приватность/удаление, базовые проверки ухода и напоминания. Прогоняем EN-матрицу и проверяем качество (T094–T099/T118/T154). | Закрыты применимые сценарии [V01–V19](quickstart.md#сквозная-приёмка); результаты fixtures, Simulator и живых интеграций записаны отдельно. Публичный выпуск требует полной приёмки. |

До первого живого среза работаем в существующем staging-окружении с постоянной тестовой учёткой. Отладка уровней доступа/квот и StoreKit идёт после него; действующие ограничения не отключаем. Комнаты T172–T174 и GitHub Actions T006 не блокируют эту очередь. Полные задачи и их зависимости остаются в [tasks.md](tasks.md): частичная проверка закрывает только указанный срез.

**Первый запуск Developer:** один узкий пакет на шаг 2, Gemini 3.8 Flash High через Antigravity. При лимите или недоступности маршрут пробует GPT-6 Luna High, затем GPT-6.1 Sol Low. Review и QA работают по прежним маршрутам. Пилот измеряет время до принятого изменения, число повторов и результаты проверок. Для нового маршрута нужен новый run ID; текущие очереди автоматически не перезапускаются.
