# Критический путь Narat до MVP

Решение 11 ноября 2026: разработка и приёмка на английском. Переключатель EN/PL и польская приёмка сняты с объёма MVP. Существующие польские данные, язык истории и совместимость форматов сохраняются. Миграция двуязычных форматов не нужна для первого прогона.

**Приоритет 12 ноября 2026.** Перед продолжением StoreKit принимаем распознавание, добавление в коллекцию и уход в одном сквозном EN-прогоне на `narat-staging`. T057 и T052 отложены до приёмки этого прогона и устранения найденных блокеров. Существующие квоты действуют.

**Обычный запуск, 15 ноября 2026.** Исторический сквозной
staging-прогон использовал специальный флаг. После исправления
обычный подписанный Release на Simulator прошёл Check a plant →
вход постоянного владельца → фото → живой результат → карточка →
та же карточка после холодного запуска. Новый EN-экран даёт прямые
входы в анализ, определение вида, каталог и коллекцию.
Исходное фото диагностики подтверждено на staging v30 до и после
перезапуска. Гостевое определение и перенос фото прошли без аргументов.
Гостевая диагностика открыта. Напоминания отложены. Следующий
прогон проверяет штатный уход сразу после сохранения.
[Отчёт](../../docs/validation/mvp-acceptance.md#v01--обычный-запуск-фотоанализ-и-сохранение).

| Порядок | Что делаем | Когда считаем пройденным |
| --- | --- | --- |
| 1. Фото → результат | В текущей подписанной сборке загрузить из галереи известное растение и отдельно непригодное фото. Сверить результаты клиента и задания провайдера (T031–T034, T037–T039, T150, T157). | Вид распознан либо явно показан `unknown`; неизвестный вид не предлагает подтверждение. Повторную диагностику, ошибки и качество отмечаем по фактическому покрытию V01–V03. |
| 2. Результат → карточка | Подтвердить вид, сохранить карточку с личным фото и открыть её после холодного запуска. Отдельно сохранить вид из каталога (T044/T046–T049/T149–T151). | API подтверждает создание. Открывается тот же ID и личное фото текущего владельца; точный повтор после потерянного ответа не создаёт дубль. |
| 3. Карточка → уход | Для сохранённой Monstera прочитать совет и источник. Записать полив, повторить запрос после потери ответа, открыть журнал после холодного запуска и отменить запись (T055–T056/T062–T068/T171). | Одна запись, видна отмена после перезапуска. Следующая проверка появляется, если она обоснована; вид без профиля не получает выдуманный совет. Полный уход принимаем по оставшимся V11/V19. |
| 4. От живого среза к выпуску | По завершении 2–3 принимаем оставшиеся ветки: каталог и identification-only (T148–T151), guest/auth, квоты и StoreKit, приватность/удаление, базовые проверки ухода и напоминания. Прогоняем EN-матрицу и проверяем качество (T094–T099/T118/T154). | Закрыты применимые сценарии [V01–V19](quickstart.md#сквозная-приёмка); результаты fixtures, Simulator и живых интеграций записаны отдельно. Публичный выпуск требует полной приёмки. |

До первого живого среза работаем в существующем staging-окружении с постоянной тестовой учёткой. Отладка уровней доступа/квот и StoreKit идёт после него; действующие ограничения не отключаем. Комнаты T172–T174 и GitHub Actions T006 не блокируют эту очередь. Полные задачи и их зависимости остаются в [tasks.md](tasks.md): частичная проверка закрывает только указанный срез.

**Первый запуск Developer:** один узкий пакет на шаг 2, Gemini 3.8 Flash High через Antigravity. При лимите или недоступности маршрут пробует GPT-6 Luna High, затем GPT-6.1 Sol Low. Review и QA работают по прежним маршрутам. Пилот измеряет время до принятого изменения, число повторов и результаты проверок. Для нового маршрута нужен новый run ID; после приёмки текущего пакета и готовности зависимостей оркестраторы сразу запускают следующий пакет без отдельного подтверждения владельца.
